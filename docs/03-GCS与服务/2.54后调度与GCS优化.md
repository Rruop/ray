## GCS 架构变更

### 1. 移除 GCS 中心化调度（Ray 2.54）

| 属性 | 内容 |
|------|------|
| **PR** | [#59979](https://github.com/ray-project/ray/pull/59979), [#60121](https://github.com/ray-project/ray/pull/60121), [#60188](https://github.com/ray-project/ray/pull/60188) |
| **版本** | Ray 2.54 |
| **影响** | 重大架构变更 |

#### 背景

Ray 历史上有两种 Actor 调度方式：

1. **默认方式（保留）**：GCS 作为 Owning Worker，委托 Raylet 进行实际调度
2. **中心化方式（移除）**：GCS 作为全局中心化调度器，完全绕过 Raylet

#### 动机

- 中心化调度方式自 2021 年引入后 (`#15943`)，从未被广泛使用
- 该功能默认关闭，且不再被支持
- 维护两套调度路径增加了代码复杂度

#### 实现方案

```
删除内容：
├── gcs_actor_scheduling_enabled 特性标志
├── GCS actor scheduler 中的中心化调度代码
├── GCS resource manager 相关代码
├── GCS placement group scheduler 相关代码
├── Raylet 中的相关代码
└── 对应的测试用例
```

**结果**：Raylet-based scheduling 成为唯一的调度路径。

### 2. 新增 ResizeRayletResourceInstances API（Ray 2.55）

| 属性 | 内容 |
|------|------|
| **PR** | [#61654](https://github.com/ray-project/ray/pull/61654), [#61666](https://github.com/ray-project/ray/pull/61666), [#61803](https://github.com/ray-project/ray/pull/61803), [#61814](https://github.com/ray-project/ray/pull/61814) |
| **版本** | Ray 2.55 |
| **功能** | 支持 In-Place Pod Resizing (IPPR) |

#### 动机

支持 Kubernetes 的 In-Place Pod Resizing 功能，允许 autoscaler 通过 GCS 动态调整 Raylet 的资源实例。

#### 实现方案

```protobuf
// autoscaler.proto
service GcsAutoscalerStateManager {
  rpc ResizeRayletResourceInstances(ResizeRayletResourceInstancesRequest)
      returns (ResizeRayletResourceInstancesReply);
}
```

**架构**：
```
Autoscaler → GCS (ResizeRayletResourceInstances) → Raylet (ResizeLocalResourceInstances)
```

**关键文件**：
- `src/ray/protobuf/autoscaler.proto`
- `src/ray/gcs/gcs_server/gcs_autoscaler_state_manager.cc`
- `src/ray/raylet_client/raylet_client.cc`

## 内存管理与资源隔离

### 1. 基于压力的内存监控（Ray 2.55）

| 属性 | 内容 |
|------|------|
| **PR** | [#61361](https://github.com/ray-project/ray/pull/61361), [#61323](https://github.com/ray-project/ray/pull/61323), [#61097](https://github.com/ray-project/ray/pull/61097), [#61210](https://github.com/ray-project/ray/pull/61210), [#61297](https://github.com/ray-project/ray/pull/61297), [#59365](https://github.com/ray-project/ray/pull/59365), [#59368](https://github.com/ray-project/ray/pull/59368), [#60752](https://github.com/ray-project/ray/pull/60752) |
| **版本** | Ray 2.55 |
| **影响** | 重大功能增强 |

#### 背景问题

现有的基于阈值的内存监控存在以下问题：

1. 周期性轮询可能错过内存突发事件
2. 杀进程策略可能不够激进
3. 无法保证工作负载内存不会影响系统进程

#### 新方案：Pressure-Based Memory Monitor

利用 Linux 的 **PSI (Pressure Stall Information)** 检测内存压力。

**工作原理**：
```
1. 监控 PSI 信息 - 追踪 cgroup 内进程等待内存资源的时间百分比
2. 使用 poll + POLLPRI 监听 memory.pressure 文件，接收内核通知
3. 根据进程等待内存的情况触发 worker killing policy
```

**技术实现**：
- 使用 cgroup v2 的 PSI 接口
- 正确的文件描述符管理和 POLLERR 错误处理
- 单元测试使用 TCP socket 模拟 POLLPRI 事件

**参考文档**：https://docs.kernel.org/accounting/psi.html

## 性能优化

### 1. 多 gRPC 连接提升对象传输吞吐量（Ray 2.55）

| 属性 | 内容 |
|------|------|
| **PR** | [#61121](https://github.com/ray-project/ray/pull/61121), [#61440](https://github.com/ray-project/ray/pull/61440) |
| **版本** | Ray 2.55 |
| **状态** | 默认启用 |

#### 动机

通过允许每个客户端创建多个 gRPC 连接来提升对象传输效率。

#### 实现方案

```cpp
// 使用 GRPC_ARG_USE_LOCAL_SUBCHANNEL_POOL 配置
// 默认每个客户端 2 个连接
RAY_CONFIG(bool, experimental_object_manager_enable_multiple_connections, true);
```

**注意**：设置最优连接数并不简单，需要在吞吐量提升和资源消耗之间权衡。

## 升级建议

### 从 2.54 升级到 2.55 时注意：

1. **GCS 中心化调度已移除**：如果之前使用 `gcs_actor_scheduling_enabled`，需要移除相关配置

2. **内存监控变更**：新的基于压力的内存监控可能改变 OOM 行为，建议在测试环境验证

3. **多 gRPC 连接默认启用**：可能增加网络资源消耗，如有问题可通过配置关闭：
   ```python
   ray.init(_system_config={"experimental_object_manager_enable_multiple_connections": False})
   ```

4. **新的 ResizeRayletResourceInstances API**：如果使用 KubeRay，可以利用此 API 实现 In-Place Pod Resizing

  关于调度和 GCS 压力优化的回答

  调度方面优化：有

  1. Label Selector API (e36060c67f): 统一调度策略，用标签选择器替代 NodeAffinitySchedulingStrategy，简化调度路径
  2. Serve 部署调度器重构 (4d958184f6): 资源建模更精确，提高调度准确性
  3. Worker killing 策略优化 (385d135f5a): 基于时间的策略可同时杀死多个 worker，更快响应内存压力

  GCS 压力方面优化：有限/间接

  1. RedisContext 优化 (1c5d04e60c): 这是对 GCS 使用的 Redis 存储客户端的内存安全改进，但不是直接的性能优化
  2. 避免多次导出 Actor class (00826118c8): 减少序列化开销，间接减轻 GCS 负担
  3. PlacementGroup 日志增强 (43d4562387): 仅是可观测性改进，非性能优化

  总结: 这 50 个 commit 中，直接针对 GCS 压力的重大优化较少，主要集中在 Ray Data 内存管理、Serve 路由稳定性和调度策略统一化方面。GCS 相关改动主要是安全性和可观测性增强。
