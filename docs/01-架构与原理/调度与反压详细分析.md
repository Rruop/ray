# Ray Data Streaming Executor 调度与反压机制分析

## 概述

本文档详细分析 Ray Data 中 `StreamingExecutor` 的调度逻辑，重点关注 `update_usages()` 方法的调用时机以及 `ResourceBudgetBackpressurePolicy` 如何受到资源管理器更新的影响。

## 2. StreamingExecutor.run() 主循环

**位置**: `streaming_executor.py`

```python
def run(self):
    """Run the control loop in a helper thread."""
    while True:
        t_start = time.perf_counter()
        continue_sched = self._scheduling_loop_step(self._topology)

        # 更新 metrics
        self.update_metrics(sched_loop_duration)

        # 执行 callbacks
        for callback in get_execution_callbacks(self._data_context):
            callback.on_execution_step(self)

        if not continue_sched or self._shutdown:
            break
```

**核心特点**:
- 在独立的守护线程中运行
- 循环调用 `_scheduling_loop_step` 直到所有算子完成
- 每次迭代后更新 metrics 并触发 execution callbacks

## 3. _scheduling_loop_step() 详细流程

**位置**: `streaming_executor.py:569-665`

### 阶段 1: 第一次更新资源使用量 (行 580)
```python
self._resource_manager.update_usages()
```
**目的**: 在处理已完成任务之前，先获取当前资源使用的最新状态。

### 阶段 2: 处理已完成的任务 (行 584-588)
```python
errored_blocks_per_op, _ = process_completed_tasks(
    topology,
    self._backpressure_policies,
    self._max_errored_blocks,
)
```
**内部操作**:
1. 收集所有活跃任务
2. 为每个算子计算 `max_bytes_to_read` (通过所有 backpressure policies 取最小值)
3. 调用 `ray.wait()` 等待任务完成
4. 批量处理 metadata refs
5. 将算子输出移动到输出队列

### 阶段 3: 第二次更新资源使用量 (行 602)
```python
self._resource_manager.update_usages()
```
**目的**: 反映已完成任务释放的资源，为调度新任务做准备。

### 阶段 4: 调度新任务循环 (行 606-627)
```python
while True:
    op = select_operator_to_run(
        topology,
        self._resource_manager,
        self._backpressure_policies,
        ensure_liveness=self._consumer_idling(),
        ranker=self._ranker,
    )

    if op is None:
        break

    topology[op].dispatch_next_task()

    self._resource_manager.update_usages()  # 第 3+ 次更新
```
**关键点**:
- 每次 dispatch 新任务后都会调用 `update_usages()`
- 这确保了每次调度决策都基于最新的资源状态
- `select_operator_to_run` 内部会查询 backpressure policies

### 阶段 5: 自动扩缩容 (行 629-631)
```python
self._cluster_autoscaler.try_trigger_scaling()
self._actor_autoscaler.try_trigger_scaling()
```

### 阶段 6: 更新算子状态 (行 640)
```python
update_operator_states(topology)
```

---

## 4. update_usages() 调用时机总结

在单次 `_scheduling_loop_step` 迭代中，`update_usages()` 被调用 **至少 2 次，通常 3+ 次**：

| 时机 | 目的 |
|------|------|
| 处理完成任务**之前** (行 580) | 获取当前资源状态 |
| 处理完成任务**之后** (行 602) | 反映释放的资源 |
| 每次 `dispatch_next_task()` **之后** (行 623) | 反映新调度任务占用的资源 |

## 5. ResourceManager.update_usages() 内部逻辑

**位置**: `resource_manager.py:200-254`

```python
def update_usages(self):
    """Recalculate resource usages."""
    # 重置全局使用量
    self._global_usage = ExecutionResources(0, 0, 0)
    self._global_running_usage = ExecutionResources(0, 0, 0)
    self._global_pending_usage = ExecutionResources(0, 0, 0)

    # 从最后一个算子向第一个算子遍历
    for op, state in reversed(self._topology.items()):
        op.update_resource_usage()
        op_usage = op.current_processor_usage()
        op_running_usage = op.running_processor_usage()
        op_pending_usage = op.pending_processor_usage()

        used_object_store = self._estimate_object_store_memory_usage(op, state)

        # 更新各种 usage 字典
        self._op_usages[op] = op_usage.copy(object_store_memory=used_object_store)
        ...

        # 累加到全局使用量
        self._global_usage = self._global_usage.add(op_usage)
        ...

    # 关键：如果启用了 OpResourceAllocator，更新分配的 budget
    if self._op_resource_allocator is not None:
        self._update_allocated_budgets()
```

### _update_allocated_budgets() (行 256-265)

```python
def _update_allocated_budgets(self):
    completed_ops_usage = self._get_completed_ops_usage()

    available_limits = (
        self.get_global_limits()
        .subtract(completed_ops_usage)
        .max(ExecutionResources.zero())
    )

    self._op_resource_allocator.update_budgets(limits=available_limits)
```

**作用**:
1. 计算已完成算子的资源使用
2. 从全局限制中减去已完成算子的使用
3. 将可用资源传递给 `OpResourceAllocator` 进行 budget 分配

## 6. ReservationOpResourceAllocator.update_budgets() 详解

**位置**: `resource_manager.py:918-1025`

这是 budget 更新的核心逻辑：

### Step 1: 更新资源预留 (_update_reservation)
```python
remaining_shared = self._update_reservation(limits)
```
- 计算每个 eligible 算子的预留资源
- 预留资源 = `reservation_ratio * global_limits / num_eligible_ops`
- 至少一半预留给算子输出

### Step 2: 计算每个算子的 budget (行 933-962)
```python
for op in eligible_ops:
    # 计算算子内存使用
    op_mem_usage = self._resource_manager.get_mem_op_internal(op)
    op_outputs_usage = self._resource_manager.get_mem_op_outputs(op, include_ineligible_downstream=True)
    op_mem_usage += max(op_outputs_usage - self._reserved_for_op_outputs[op], 0)

    # 计算剩余预留
    op_reserved_remaining = op_reserved.subtract(op_usage).max(ExecutionResources.zero())

    # 设置 budget = 剩余预留
    self._op_budgets[op] = op_reserved_remaining
```

### Step 3: 分配共享资源 (行 967-1005)
```python
for i, op in enumerate(reversed(eligible_ops)):
    # 平均分配剩余共享资源
    op_shared = remaining_shared.scale(1.0 / (len(eligible_ops) - i))

    # 如果算子 budget 不足以调度最小任务，允许借用资源
    to_borrow = op.min_scheduling_resources().subtract(self._op_budgets[op].add(op_shared))
    if not to_borrow.is_zero() and op_shared.add(to_borrow).satisfies_limit(remaining_shared):
        op_shared = op_shared.add(to_borrow)

    self._op_budgets[op] = self._op_budgets[op].add(op_shared)
```

### Step 4: 特殊处理 materializing operators (行 1020-1024)
```python
for op in eligible_ops:
    if self._resource_manager._is_blocking_materializing_op(op):
        self._op_budgets[op] = self._op_budgets[op].copy(
            object_store_memory=float("inf")
        )
```
**原因**: `AllToAllOperator` 等 materializing 算子需要等待所有输入完成，禁用其 object store 内存反压以避免死锁。

## 7. ResourceBudgetBackpressurePolicy 工作机制

**位置**: `resource_budget_backpressure_policy.py`

```python
class ResourceBudgetBackpressurePolicy(BackpressurePolicy):
    """A backpressure policy based on resource budgets in ResourceManager."""

    @property
    def name(self) -> str:
        return "ResourceBudget"

    def can_add_input(self, op: "PhysicalOperator") -> bool:
        if self._resource_manager._op_resource_allocator is not None:
            return self._resource_manager._op_resource_allocator.can_submit_new_task(op)
        return True

    def max_task_output_bytes_to_read(self, op: "PhysicalOperator") -> Optional[int]:
        return self._resource_manager.max_task_output_bytes_to_read(op)
```

### 两种反压机制：

#### 7.1 任务提交反压 (can_add_input)

**调用链**:
```
select_operator_to_run()
  -> get_eligible_operators()
      -> policy.can_add_input(op)
          -> _op_resource_allocator.can_submit_new_task(op)
```

**can_submit_new_task() 实现** (行 860-874):
```python
def can_submit_new_task(self, op: PhysicalOperator) -> bool:
    budget = self.get_budget(op)

    if budget is None:
        return True

    return (
        op.incremental_resource_usage().satisfies_limit(budget)
        and
        # 避免调度如果没有足够的 Object Store budget (用于任务输出)
        budget.object_store_memory >= (op.metrics.obj_store_mem_max_pending_output_per_task or 0)
    )
```

**反压条件**:
1. 算子的增量资源使用超过当前 budget
2. 或者 object_store_memory budget 不足以容纳预估的任务输出

#### 7.2 输出反压 (max_task_output_bytes_to_read)

**调用链**:
```
process_completed_tasks()
  -> policy.max_task_output_bytes_to_read(op)
      -> _resource_manager.max_task_output_bytes_to_read(op)
          -> _op_resource_allocator.max_task_output_bytes_to_read(op)
```

**max_task_output_bytes_to_read() 实现** (行 896-916):
```python
def max_task_output_bytes_to_read(self, op: PhysicalOperator) -> Optional[int]:
    if op not in self._op_budgets:
        return None

    res = self._op_budgets[op].object_store_memory
    # 加上 _reserved_for_op_outputs 的剩余部分
    op_outputs_usage = self._resource_manager.get_mem_op_outputs(op, include_ineligible_downstream=True)
    res += max(self._reserved_for_op_outputs[op] - op_outputs_usage, 0)

    if math.isinf(res):
        return None

    res = int(res)
    if res == 0 and self._should_unblock_streaming_output_backpressure(op):
        res = 1  # 特殊情况：允许读取 1 字节以避免死锁

    return res
```

## 9. Budget 与反压的关键关系

### Budget 计算公式
```
budget = allocation - usage
       = (reserved + shared) - (internal_usage + outputs_usage_exceeding_reserved)
```

### 反压触发条件

| 反压类型 | 触发条件 | 影响 |
|----------|----------|------|
| **任务提交反压** | `op.incremental_resource_usage() > budget` | 算子无法调度新任务 |
| **输出反压** | `budget.object_store_memory == 0` | 限制从已完成任务读取输出 |

### 反压解除条件

1. **任务完成**: 释放 CPU/GPU/内存资源
2. **下游算子消费数据**: 减少上游算子的 `op_outputs_usage`
3. **资源被释放**: `update_usages()` 重新计算 budget

---

## 10. 总结

1. **update_usages() 是反压机制的核心驱动力** - 每次调用都会重新计算所有算子的 budget
2. **在单次调度迭代中被调用多次** (至少 2 次，每次 dispatch 后还会额外调用)
3. **ResourceBudgetBackpressurePolicy 是"无状态"的** - 它只是查询 ResourceManager 的当前状态
4. **真正的状态在 _op_budgets 字典中** - 由 `ReservationOpResourceAllocator.update_budgets()` 维护
5. **两种反压协同工作**:
   - 任务提交反压：控制新任务的调度
   - 输出反压：控制从已完成任务读取输出的速率
