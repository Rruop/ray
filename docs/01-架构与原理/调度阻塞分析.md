# Ray Data Streaming Executor 调度阻塞问题分析

## 问题描述

用户观察到三个警告信息之间存在较长的时间间隔（约18分钟），且 `_scheduling_loop_step` 之间间隔很久：

1. `23:36:28` - API server 等待响应: `Waiting for the response from the API server address http://10.137.75.19:8265/api/v0/tasks`
2. `23:36:28` - Scheduler 日志显示所有 operators 不可调度，`Map(VideoClipProcessMapper)` 因 `backpressure(ConcurrencyCap)` 阻塞
3. `23:54:55` - Hanging task 警告: 任务运行了 199.99s，远超平均 17.16s
4. `23:54:55` - 资源不足警告: `Cluster resources are not enough to run any task from TaskPoolMapOperator[ReadParquet]`

---

## 根本原因

**API Server 响应慢 + `HangingExecutionIssueDetector` 在调度循环关键路径上同步调用 `get_task()` = 阻塞整个调度循环**

---

## 详细调用链分析

### 1. 主调度循环 (`streaming_executor.py:455-480`)

```python
def run(self):
    while True:
        # 1. 执行一轮调度步骤
        continue_sched = self._scheduling_loop_step(self._topology)

        # 2. ⚠️ 执行 callbacks - 这里会阻塞下一轮循环！
        for callback in get_execution_callbacks(self._data_context):
            callback.on_execution_step(self)  # <-- issue_detector 在这里执行

        if not continue_sched or self._shutdown:
            break
```

### 2. `_scheduling_loop_step` 内部流程 (`streaming_executor.py:569-665`)

```python
def _scheduling_loop_step(self, topology: Topology) -> bool:
    # 1. 更新资源使用量 (本地计算，快速)
    self._resource_manager.update_usages()

    # 2. 处理完成的任务 (最多阻塞 0.1 秒)
    errored_blocks_per_op = process_completed_tasks(
        topology,
        self._backpressure_policies,
        self._max_errored_blocks,
    )
    # 内部调用 ray.wait(timeout=0.1)

    # 3. 选择并调度 operators (本地计算)
    while True:
        op = select_operator_to_run(...)  # 调用 get_eligible_operators()
        if op is None:
            break
        topology[op].dispatch_next_task()  # 提交 Ray task (非阻塞)

    # 4. 触发自动扩缩容 (异步调用)
    self._cluster_autoscaler.try_trigger_scaling()
    self._actor_autoscaler.try_trigger_scaling()

    # 5. 同步配置 (有节流，通常快速)
    if self._config_controller:
        self._config_controller.try_apply_config()

    # 6. 更新状态 (本地)
    update_operator_states(topology)

    return not all(op.has_completed() for op in topology)
```

### 3. Issue Detection Callback (`insert_issue_detectors.py:21-23`)


### 4. Issue Detector Manager (`issue_detector_manager.py:40-55`)

```python
def invoke_detectors(self) -> None:
    curr_time = time.perf_counter()
    for detector in self._issue_detectors:
        # 每 30 秒执行一次检测
        if curr_time - self._last_detection_times[detector] > detector.detection_time_interval_s():
            issues.extend(detector.detect())  # ⚠️ 可能很慢！
            self._last_detection_times[detector] = time.perf_counter()
    self._report_issues(issues)
```

### 5. Hanging Detector - 阻塞点！ (`hanging_detector.py:132-210`)

```python
def detect(self) -> List[Issue]:
```

```python
@contextmanager
def warnings_on_slow_request(*, address: str, endpoint: str, timeout: float, explain: bool):

    warning_timers = [
        threading.Timer(timeout / i, print_warning, args=[timeout / i])
        for i in [2, 4, 8]
    ]
```

## 时间阻塞分析

假设场景：
- `VideoClipProcessMapper` 有 **50 个 running tasks**
- API Server 响应慢，每次 `get_task()` 等待接近 1 秒

阻塞时间计算：
```
50 tasks × 1 秒/task = 50 秒阻塞
```

这就解释了为什么 `_scheduling_loop_step` 之间隔了很久：
- 正常情况：每轮 ~0.1 秒 (`ray.wait` timeout)
- API Server 慢时：每 30 秒的 issue detection 可能阻塞 **几十秒甚至几分钟**

## Backpressure 机制说明

### `backpressure(ConcurrencyCap)` 的含义

`ConcurrencyCapBackpressurePolicy` (`concurrency_cap_backpressure_policy.py`) 是动态并发控制策略：

```python
class ConcurrencyCapBackpressurePolicy(BackpressurePolicy):
    """
    通过监控输出队列字节数动态调整并发：
    - 维护 EWMA 估算典型队列水平和标准差
    - 定义 deadband: [level - K_DEV*dev, level + K_DEV*dev]
    - q > upper → 减少并发 (回退)
    - q < lower → 增加并发 (提升)
    """

    def can_add_input(self, op: PhysicalOperator) -> bool:
        # 如果 running_tasks >= effective_cap，返回 False
        # 触发 backpressure(ConcurrencyCap)
        return num_tasks_running < effective_cap
```

### `no_pending_bundles` 的含义

```python
# streaming_executor_state.py:209-210
def has_pending_bundles(self) -> bool:
    return any(len(q) > 0 for q in self.input_queues)
```

当 operator 的所有输入队列都为空时，该 operator 被标记为 `no_pending_bundles`。

## 解决方案

### 1. 临时方案 - 禁用 Issue Detection

```python
import ray.data

# 禁用所有 issue detectors
ray.data.DataContext.get_current().issue_detectors_config.detectors = []
```

### 2. 排查 API Server 为什么慢

- 检查 Ray Dashboard 的负载
- 检查 GCS 的负载和响应时间
- 检查网络延迟

### 3. 代码层面修复建议

**问题核心**：Issue detection 在调度循环的关键路径上同步执行

**建议修复**：
1. 把 issue detection 放到独立线程或异步执行
2. 或者限制每轮检测的 `get_task()` 调用次数
3. 或者使用批量 API 获取任务状态，而不是逐个调用

```python
# 可能的改进方向
class IssueDetectionExecutionCallback(ExecutionCallback):
    def __init__(self):
        self._executor = ThreadPoolExecutor(max_workers=1)
        self._pending_detection = None

    def on_execution_step(self, executor):
        # 异步执行，不阻塞调度循环
        if self._pending_detection is None or self._pending_detection.done():
            self._pending_detection = self._executor.submit(
                executor._issue_detector_manager.invoke_detectors
            )
```

## 总结

1. **API Server 响应慢**会直接影响调度循环，因为 `HangingExecutionIssueDetector` 在关键路径上同步调用 `get_task()`

2. **调度循环本身没有停**，`ray.wait(timeout=0.1)` 只阻塞 0.1 秒，但 **issue detection callback 阻塞了下一轮循环的开始**

3. **日志间隔长**是因为 `on_execution_step()` 中的 API 调用阻塞了整个调度线程

4. **`backpressure(ConcurrencyCap)`** 是正常的流控机制，与 API Server 问题无关

5. **建议**：临时禁用 issue detection，或排查 API Server 响应慢的根因
