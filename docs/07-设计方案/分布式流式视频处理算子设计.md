# DistributedStreamingVideoProcessMapper 设计文档

## 概述

`DistributedStreamingVideoProcessMapper` 是一个分布式流式视频处理算子，将 CPU 密集型的预处理任务分布到远程 Actor 执行，GPU Worker 专注于推理任务，实现 CPU/GPU 并行流水线。

## 架构设计

### 核心思想

```
┌─────────────────────────────────────────────────────────────────┐
│                    GPU Worker (Mapper)                          │
│  ┌─────────────┐    ┌─────────────┐    ┌─────────────┐         │
│  │  submit()   │───▶│  ray.wait() │───▶│ GPU 推理    │         │
│  │  prefetch   │    │  + ray.get()│    │             │         │
│  └─────────────┘    └─────────────┘    └─────────────┘         │
└─────────────────────────────────────────────────────────────────┘
         │                    ▲
         │ remote()           │ ObjectRef
         ▼                    │
┌─────────────────────────────────────────────────────────────────┐
│              CPU Actor Pool (分布式预处理)                       │
│  ┌──────────┐  ┌──────────┐  ┌──────────┐  ┌──────────┐        │
│  │ Actor 0  │  │ Actor 1  │  │ Actor 2  │  │ Actor 3  │        │
│  │ 下载+解码 │  │ 下载+解码 │  │ 下载+解码 │  │ 下载+解码 │        │
│  │ +预处理   │  │ +预处理   │  │ +预处理   │  │ +预处理   │        │
│  └──────────┘  └──────────┘  └──────────┘  └──────────┘        │
└─────────────────────────────────────────────────────────────────┘
```

### 与 StreamingVideoProcessMapper 的区别

| 特性 | StreamingVideoProcessMapper | DistributedStreamingVideoProcessMapper |
|------|---------------------------|---------------------------------------|
| CPU 预处理 | GPU Worker 本地执行 | 分布到远程 Actor 执行 |
| GPU 利用率 | 被 CPU 任务阻塞 | 专注推理，不被阻塞 |
| 扩展性 | 受单机 CPU 限制 | 可利用集群 CPU 资源 |
| 数据传输 | 无需传输 | 通过 Ray Object Store |

## 处理流程

### 流水线模式

1. **构建批次**：将 segments 按 `batch_size` 分组
2. **预提交**：使用轮询方式向 Actor 提交 `prefetch_batches` 个批次
3. **等待结果**：使用 `ray.wait()` 带 timeout 获取完成的批次
4. **顺序处理**：通过 `results_buffer` 和 `next_process_idx` 保证顺序
5. **GPU 推理**：对预处理完成的数据执行 embedding 提取和分类
6. **补充提交**：处理完一批后补充提交下一批，保持流水线

### 顺序处理机制

```python
# results_buffer: {batch_idx: results}
# next_process_idx: 下一个要处理的批次索引

# 按顺序处理已完成的批次
while next_process_idx in results_buffer:
    batch_result = results_buffer.pop(next_process_idx)
    if batch_result is None:
        # 该批次失败，跳过
        skip_batch_segments(...)
    else:
        process_batch_results(next_process_idx, batch_result)
    next_process_idx += 1
```

**工作原理**：
- `while next_process_idx in results_buffer` 检查当前期望的批次是否已完成
- 如果 batch 0 在 buffer 中，处理它并将 `next_process_idx` 增加到 1
- 如果 batch 1 也在 buffer 中，继续处理，以此类推
- 这确保即使结果乱序到达，也能按顺序处理

## 容错机制

### Ray Core 内置容错

使用 Ray 的内置容错机制，而非手动管理 Actor 生命周期：

```python
CPsActorWithResources = CPUPreprocessActor.options(
    num_cpus=self.cpu_actor_num_cpus,
    memory=self.cpu_actor_memory,
    max_restarts=-1,      # 无限重启
    max_task_retries=3,   # 任务级重试
)
```

### 异常处理位置

| 操作 | 异常可能性 | 处理方式 |
|------|-----------|---------|
| `remote()` | 不会抛异常（`max_restarts=-1`） | Ray 自动排队等待 Actor 恢复 |
| `ray.wait()` | 不会抛异常 | 返回 `(ready, not_ready)` 元组 |
| `ray.get()` | 可能抛异常 | 捕获并标记批次失败 |

### ray.get() 异常类型

- `GetTimeoutError`: Object Store 获取超时
- `RayActorError`: Actor 崩溃
- `RayTaskError`: 任务执行失败
- 其他 `Exception`: 通用错误

## 配置参数

### 参数列表

| 参数 | 默认值 | 说明 |
|------|-------|------|
| `cpu_actor_pool_size` | 4 | CPU Actor 数量 |
| `cpu_actor_num_cpus` | 2 | 每个 Actor 的 CPU 数量 |
| `cpu_actor_memory` | 3GB | 每个 Actor 的内存限制 |
| `batch_size` | 8 | 每批处理的 segment 数量 |
| `prefetch_batches` | 2 | 预取的批次数量 |
| `batch_timeout_sec` | 120.0 | 每批处理的超时时间（秒）|
| `actor_num_workers` | 4 | Actor 内部并发线程数 |
| `gc_interval` | 10 | GC 调用间隔（每处理多少 segment 执行一次）|

### 参数配置建议

#### 1. CPU Actor Pool 配置

**`cpu_actor_pool_size`（Actor 数量）**

```
推荐值: 与 GPU Worker 数量相当或略多
计算方式: streaming_gpu_concurrency * 2 ~ 4
```

| 场景 | GPU Worker 数 | 推荐 Actor 数 | 理由 |
|------|--------------|---------------|------|
| 小规模 | 2 | 4-8 | 保证流水线不断 |
| 中规模 | 4 | 8-16 | 平衡资源利用 |
| 大规模 | 8+ | 16-32 | 充分利用集群 CPU |

**`cpu_actor_num_cpus`（每 Actor CPU 数）**

```
推荐值: 2
范围: 1-4
```

- 视频解码和预处理可并行，2 CPU 足够
- 过多 CPU 会导致调度困难

**`cpu_actor_memory`（每 Actor 内存）**

```
推荐值: 3GB (3 * 1024 * 1024 * 1024)
范围: 2GB - 6GB
```

| 视频类型 | 推荐内存 |
|---------|---------|
| 短视频（<1min）| 2-3GB |
| 中等视频（1-5min）| 3-4GB |
| 长视频（>5min）| 4-6GB |

#### 2. 批处理配置

**`batch_size`（每批 segment 数）**

```
推荐值: 8
范围: 4-16
```

| batch_size | 优点 | 缺点 |
|------------|------|------|
| 4 | 响应快，内存压力小 | 调度开销大 |
| 8 | 平衡性能和响应 | 通用选择 |
| 16 | 吞吐高 | 内存压力大，延迟高 |

**`prefetch_batches`（预取批次数）**

```
推荐值: 2
范围: 1-4
```

- 2 个预取批次足以隐藏网络延迟
- 过多预取会增加内存压力

**计算公式**：
```
in-flight segments = prefetch_batches × batch_size × cpu_actor_pool_size
推荐 in-flight segments < 100
```

#### 3. 超时配置

**`batch_timeout_sec`（批次超时）**

```
推荐值: 120.0 秒
范围: 60.0 - 300.0 秒
```

| 场景 | 推荐超时 | 理由 |
|------|---------|------|
| 快速网络 + 短视频 | 60-90s | 加快失败恢复 |
| 一般场景 | 120s | 平衡稳定性和响应 |
| 慢网络 + 长视频 | 180-300s | 避免误判超时 |

#### 4. 并发配置

**`actor_num_workers`（Actor 内部线程数）**

```
推荐值: 4
范围: 2-8
```

- 匹配 `batch_size`，确保批次内并发处理
- 推荐：`actor_num_workers = batch_size / 2` 或 `batch_size`

### 资源估算

```
总 CPU 需求 = cpu_actor_pool_size × cpu_actor_num_cpus + streaming_gpu_concurrency × streaming_num_cpus
总内存需求 = cpu_actor_pool_size × cpu_actor_memory + GPU Worker 内存
```

**示例（中规模）**：
- CPU Actors: 8 × 2 = 16 CPUs
- GPU Workers: 4 × 1 = 4 CPUs
- 总 CPU: 20 CPUs
- 内存: 8 × 4GB = 32GB（Actor）+ GPU Worker 内存

## 调优建议

### 1. GPU 利用率低

**症状**: GPU 等待 CPU 预处理

**解决方案**:
- 增加 `cpu_actor_pool_size`
- 增加 `prefetch_batches`
- 增加 `batch_size`

### 2. 内存压力大

**症状**: OOM 或频繁 GC

**解决方案**:
- 减少 `batch_size`
- 减少 `prefetch_batches`
- 减少 `cpu_actor_memory`
- 减少 `gc_interval`

### 3. 超时频繁

**症状**: 大量批次超时失败

**解决方案**:
- 增加 `batch_timeout_sec`
- 检查网络和存储性能
- 减少 `batch_size`（减少单批处理时间）

### 4. 调度延迟高

**症状**: 批次提交慢

**解决方案**:
- 减少 `cpu_actor_pool_size`（避免调度压力）
- 确保集群有足够资源

## 设计决策记录

### 1. 为什么使用轮询而不是 ActorPool？

Ray Data 的 `ActorPoolStrategy` 具有 locality-aware + 负载均衡特性，但对于这种流水线场景，简单的轮询分配足够有效，且代码更简单。

### 2. 为什么移除手动 Actor 健康检查？

使用 Ray Core 的 `max_restarts=-1` 和 `max_task_retries=3` 配置，由 Ray 自动处理 Actor 恢复和任务重试，避免复杂的手动生命周期管理。

### 3. 为什么使用 results_buffer 保证顺序？

视频处理需要保持 segment 顺序，以正确检测 multi-shot 边界。乱序处理会导致分类器上下文错误。

### 4. 为什么 remote() 不需要 try-catch？

当 `max_restarts=-1` 时，Ray 会自动排队等待 Actor 恢复，`remote()` 调用不会抛出异常。异常只在 `ray.get()` 时才会暴露。
